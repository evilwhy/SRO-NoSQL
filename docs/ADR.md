# ADR-001. Кэш расписания: Redis поверх MongoDB

Дата: 2026-10-20

## Контекст

Расписание университета читают очень много и очень часто (студенты открывают свою группу по несколько раз в день, особенно утром и на переменах), а меняют редко (деканат переносит пару раз в несколько дней). Основное хранилище должно держать группы, преподавателей, аудитории и занятия, а запрос "расписание группы на неделю" собирается из четырех коллекций и при пиковой нагрузке становится дорогим.

Нужно: быстрое чтение готового расписания, при этом после переноса пары студенты не должны долго видеть старую аудиторию.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только MongoDB, индексы | одна система, данные всегда свежие | каждый запрос собирает расписание через $lookup, при пике нагрузки это лишняя работа на каждое открытие страницы |
| B. Только Redis | очень быстро | нет нормальных запросов (свободные аудитории, нагрузка преподавателя), данные плоские, нет надежного хранения истории |
| C. PostgreSQL + кэш | привычные JOIN | для расписания жесткая схема не нужна, а кэш все равно придется добавлять, то есть тот же вариант D, только с SQL |
| D. MongoDB + Redis (cache-aside) | Mongo хранит и отвечает на сложные запросы, Redis отдает готовое расписание за доли мс | две системы, нужно следить за согласованностью кэша |

## Решение

Вариант D. MongoDB как основное хранилище (коллекции groups, teachers, rooms, lessons), Redis как кэш готовых расписаний по шаблону cache-aside.

- ключи: `schedule:group:<код>`, `schedule:teacher:<id>`, `schedule:room:<аудитория>`, значение JSON расписания на неделю
- TTL 300 секунд (страховка на случай, если инвалидация не сработала)
- после любого изменения занятия приложение удаляет ключи группы, преподавателя и аудитории, причем и старые, и новые значения (если пару перенесли в другую аудиторию, устарели оба расписания аудиторий)
- расписание на день не кэшируется отдельно, оно фильтруется из недельного в приложении, чтобы ключей было меньше и инвалидация была проще

## Последствия

Плюс: горячие чтения идут в Redis, Mongo нагружена только промахами и записью. Сложные запросы (свободные аудитории, конфликты, нагрузка) остаются в Mongo.

Минус: окно устаревших данных не нулевое. При удалении ключа после записи оно практически ноль, при гонке читателя и писателя (читатель прочитал старое из Mongo до записи, а положил в кэш после DEL) может доходить до TTL. Поэтому TTL оставлен небольшим. Второй минус: инвалидацию делает приложение, если менять lessons напрямую в Mongo мимо сервиса, кэш об этом не узнает до истечения TTL.

Отвергнуто: write-through (писать в кэш сразу новое расписание) - при переносе одной пары пришлось бы пересобирать до шести расписаний на каждое изменение, а изменений мало и их читают не сразу; проще удалить и собрать по первому запросу.
